# 기상청 자료 → 구글 시트 자동 갱신 설계 (Pi 연결 시 트리거)

작성: 2026-11-11 · 대상: sc-sensors 저장소(Pi `~/smart-cabin`), 구글 시트「동지집 기온·습도 기록」, `sheets/Code.gs`
상태: 설계안. 지금은 Claude가 수동으로 갱신하고, 이 설계대로 구현되면 수동 갱신을 대체한다.

## 1. 목표

- Pi가 인터넷에 붙는 순간(핫스팟 켜짐, 나중에 KT 상시회선) 밀린 기상 자료를 시트에 채운다.
- 붙어 있는 동안은 발표 주기에 맞춰 계속 갱신한다.
- 인터넷이 없으면 아무 것도 하지 않는다(난방 제어는 지금처럼 로컬로 독립).
- 시트에 쓰는 형식은 지금 수동 갱신과 똑같이 맞춘다 → `농막_현재` 10행 아래 대시보드가 그대로 동작.

## 2. 이미 있는 것 (재사용)

| 구성 | 위치 | 하는 일 |
|---|---|---|
| `weather/forecast_fetch.py` | Pi | 단기예보(격자 57,99) → `forecast.json`, `forecast_hist.csv`. 오프라인이면 즉시 종료 |
| `weather/kma_obs_fetch.py` | Pi, cron 매시 15분 | ASOS 부여(236) 시간자료 최근 6h → `kma_obs.csv` (멱등, 백필 인자 지원) |
| `kma.env` | Pi, 저장소 밖 | `KMA_AUTH_KEY`. 코드·로그에 찍지 않음 |
| 웹앱 `Code.gs` doPost | 구글 | `secret` 확인 후 mode별로 탭에 기록 (current / hourly / avg / presence …) |
| `sheet_cmd_poll.py` | Pi, 매분 | `명령` 탭 폴링 → 명령 실행 |

## 3. 구조 (권장안 A: Pi가 받아서 올린다)

```
[NetworkManager 연결/인터넷 확인] ──┐
[systemd timer 매시 12·42분] ───────┼─▶ kma-sync.service (oneshot)
[명령 탭 '기상'] ──(sheet_cmd_poll)─┘        │
                                             ├─ 0) 시계 확인(NTP 동기화 안 됐으면 중단)
                                             ├─ 1) forecast_fetch.py   (단기예보, 최신 발표)
                                             ├─ 2) kma_obs_fetch.py    (관측 시간자료, 마지막 업로드 이후 백필)
                                             ├─ 3) mid_fetch.py (신규) (중기 육상·기온)
                                             ├─ 4) daily_fetch (신규)   (부여 일자료 확정 + 오늘 잠정)
                                             └─ 5) sheet_weather_push.py (신규) ─POST mode:"weather"─▶ Code.gs
                                                                                    └─ 탭 기록 + 안내!A14 시각
```

### 왜 A인가
- 인증키가 지금처럼 Pi의 `kma.env`에만 있다(구글에 키를 하나 더 두지 않음).
- 이미 검증된 수집기 두 개를 그대로 쓴다. 같은 자료로 난방 예열(`forecast.json`)과 시트가 맞물린다.
- 사용자가 원한 "Pi가 붙으면 갱신" 동작과 일치한다.

### 대안 B (참고): 구글이 직접 받는다
- `kma.gs`가 Apps Script 시간 트리거로 기상청을 직접 조회. 인증키는 스크립트 속성.
- 장점: Pi가 꺼져 있어도 시트가 갱신된다(기상 자료는 원래 Pi와 무관). Pi 시계 문제도 없다.
- 단점: 키가 두 곳, 수집 코드 이중화, 기상청 서버가 구글 IP를 끊을 가능성은 미확인.
- 결론: 우선 A로 가고, KT 상시회선 전까지 "부재 중 공백"이 불편하면 B를 보조로 추가(같은 mode:"weather" 기록 함수를 재사용).

## 4. Pi 쪽

### 4-1. 트리거
1. **NetworkManager 디스패처** `/etc/NetworkManager/dispatcher.d/90-kma-sync`
   - 이벤트 `up`, `connectivity-change`(CONNECTIVITY_STATE=FULL)에서만
   - `systemctl start --no-block kma-sync.service` 한 줄(디스패처는 짧게 끝나야 함)
2. **systemd timer** `kma-sync.timer`: `OnCalendar=*-*-* *:12,42:00`, `Persistent=true`
   - 단기예보 발표(02·05·…시 +10분), 관측(정시 +10분)을 놓치지 않는 간격
   - 오프라인이면 스크립트가 즉시 종료하므로 비용 없음
3. **명령 탭 `기상`**: `sheet_cmd_poll.py`에 한 줄 추가 → 같은 서비스 시작. 휴대폰에서 즉시 갱신용.
4. 기존 cron(`kma_obs_fetch` 매시 15분)은 이 서비스로 흡수하고 지운다(중복 실행 방지).

### 4-2. `kma-sync.service`
- `Type=oneshot`, `User=ryuch`, `WorkingDirectory=/home/ryuch/smart-cabin`, `EnvironmentFile=/home/ryuch/smart-cabin/kma.env` + `gateway.env`(SECRET, WEBAPP_URL)
- `ExecStart=/usr/bin/flock -n /tmp/kma-sync.lock python3 weather/kma_sync.py`
- `TimeoutStartSec=300`

### 4-3. `weather/kma_sync.py` (신규, 오케스트레이터)
순서와 규칙:
0. **시계 확인**: `timedatectl show -p NTPSynchronized --value` = `yes`가 아니면 최대 60초 기다렸다가 그래도 아니면 종료(로그 남김). RTC 없는 Pi가 몇 일 뒤처진 시계로 발표시각을 고르는 사고를 막는다(11/1 사례).
1. **온라인 확인**: 기존 `_online()` 재사용. 오프라인이면 0으로 종료.
2. **할 일 판정**(상태 파일 `kma_sync_state.json`):
   - 단기예보: 새 발표(최신 base)가 이전 업로드 base와 다를 때만
   - 관측: 시트 마지막 시각(웹앱 doGet으로 조회) 이후 ~ 현재 정시. 31일 넘으면 31일씩 나눠 백필
   - 일자료: 어제 확정이 안 올라갔으면 확정 + 오늘 잠정(분 자료로 최저·최고 시각)
   - 중기: 06:00/18:00 발표가 새로 나왔을 때
   - `--force`면 전부
3. 각 수집은 기존 스크립트 함수를 import해서 호출(서브프로세스 대신). 기상청 연결 끊김 대비 5회 재시도·3초 간격.
4. `sheet_weather_push.py`로 한 번에 업로드. 실패하면 상태 파일을 갱신하지 않아 다음 실행에서 다시 시도.
5. 로그 `kma_sync.log`: 시각, 한 일, 행 수, 실패 사유. 인증키·SECRET은 절대 찍지 않음.

### 4-4. 업로드 페이로드 (mode:"weather")
```json
{
  "secret": "...", "mode": "weather", "fetched_at": "2026-11-11T11:20:00+09:00",
  "vilage": {"base_prev": "202611102300", "base": "202611111100",
             "rows": [["2026-11-11 00:00", 4, 85, 0, "강수없음", "맑음", 0.1], ...81행]},
  "obs_hourly": [["2026-11-11 10:00", 8.9, 77, 0, 0], ...],
  "obs_daily":  [["2026-11-10", -1.2, "07:20", 14.9, "14:13", 5.9, -4.5, 78.4, 31, 0, 1.1, 100, ""], ...],
  "mid": {"tmfc": "202611110600", "rows": [["2026-11-15","흐리고 비","구름많음",60,20,12,18,"4일째"], ...]}
}
```
- 행 형식은 지금 수동 갱신과 동일(시트 열 순서 그대로).
- 시각은 KST 문자열. 시트에서 날짜로 해석되게 Code.gs가 `new Date()`로 바꿔 쓴다.

## 5. 구글 쪽 (`Code.gs`에 mode:"weather" 추가, 버전 v11)

| 대상 탭 | 쓰는 방식 | 주의 |
|---|---|---|
| `동지집_예보` | A3:G83 덮어쓰기 + A1 설명(발표시각 두 개, 조회 시각) | W~Z 비교 수식은 건드리지 않음 |
| `예보검증` | 23시 발표분이 오면 다음날 24행을 맨 아래에 추가 | 같은 날짜 있으면 건너뜀 |
| `부여_시간별` | 마지막 시각 이후만 추가(시각 키로 중복 제거) | 열린 범위 수식(`$B$2:$B`)이 있어 **끝에 추가만**, 중간 삽입 금지 |
| `부여_일별` | 날짜 키로 있으면 덮어쓰기, 없으면 추가. 잠정 행은 M열 비고 | 확정되면 비고 지움 |
| `중기예보` | A1 설명 + A3:H9 덮어쓰기 | 기온 지점 11C20501(부여), 날씨 11C20000(충남) |
| `안내` A14 | "마지막 조회 …" 갱신 | |
| `농막_현재` | **건드리지 않음** | 10행 아래 대시보드는 수식이라 자동 반영 (1~4행 센서는 Pi가 기록) |

- `LockService.getScriptLock()`으로 동시 기록 방지(센서 업로드와 겹칠 수 있음).
- 응답: `{ok, vilage:{rows}, obs_hourly:{added}, obs_daily:{updated,added}, mid:{rows}}` → Pi 로그에 남김.
- doGet 응답에 `weather_last` (부여_시간별 마지막 시각, 예보 base, 중기 tmFc) 추가 → Pi가 "무엇을 백필할지" 판단.

## 6. 실패와 예외

| 상황 | 동작 |
|---|---|
| 오프라인 | 즉시 종료. 다음 연결 때 디스패처가 다시 실행 |
| Pi 시계 미동기화 | 종료(로그). 잘못된 base·잘못된 "오늘"을 막음 |
| 기상청 연결 끊김 | 5회 재시도 후 그 항목만 실패, 나머지는 업로드 |
| 웹앱 오류·SECRET 불일치 | 상태 파일 갱신 안 함 → 다음 실행에서 재시도 |
| 핫스팟 잠깐 켰다 끔 | flock으로 중복 방지. 중간에 끊기면 다음에 이어서 |
| 며칠 오프라인 후 연결 | 관측은 doGet 마지막 시각부터 백필(31일 단위), 예보는 최신 발표만 |
| 데이터 사용량 | 1회 약 200~300KB(단기예보 JSON이 대부분). 하루 48회여도 15MB 이하 → 농막 회선 6GB에 영향 없음 |

## 7. 구현·검증 순서

1. Code.gs v11: mode:"weather" 기록 함수 + doGet `weather_last`. 시험용 복사 시트에서 페이로드 직접 POST로 확인.
2. `kma_sync.py` + `sheet_weather_push.py` + `mid_fetch`/`daily_fetch` 함수. `--dry-run`(업로드 대신 페이로드 출력)으로 지금 수동 갱신 결과와 값 비교.
3. systemd 유닛·타이머·디스패처 설치(PI_SETUP.md에 절차 추가). sudo 비밀번호는 사용자가 입력.
4. 현장 시험: 핫스팟 끔 → 켬 → 1분 안에 `안내!A14`와 대시보드 "부여 관측소 갱신"이 바뀌는지 확인.
5. 1주 운영 후 기존 cron 정리, 수동 갱신 중단.

## 8. 지금(수동 단계)에서 지킬 형식
- `동지집_예보`: 오늘 00시부터 81행, 오늘 앞 시간은 이전 발표로 채움, A1에 발표·조회 시각.
- `부여_시간별`: 끝에 추가만.
- `부여_일별`: 마지막 행은 잠정(M열 비고), 다음 갱신 때 확정.
- `중기예보`: A1 설명 + 3~9행.
- `안내!A14`: 마지막 조회 시각.
