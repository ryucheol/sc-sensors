# Shelly Plug M Gen3 — 기능 조사와 농막 적용

> 2026-11-13 작성. 투야 플러그를 대신할 Shelly Plug M Gen3를 집에서 시험한 기록과, 플러그 안에서 도는 **Pi 독립 동파 가드**의 설계·검증·설치 절차.
> 비밀값(센서 bindkey, 기상청 인증키, 플러그 비밀번호)은 이 문서와 저장소에 쓰지 않는다. 플러그 내부 저장소(KVS)와 Pi의 gitignore 파일에만 둔다.

## 2. 기능 조사 (플러그에 `Shelly.ListMethods`로 직접 확인 + 공식 문서)

**안전·보호**
- 과전력·과전류·과전압·저전압 차단, 과열(`overtemp`) 차단. 오류는 `Switch.GetStatus.errors`에 남는다.
- 내부 온도(`temperature.tC`)를 늘 읽을 수 있다. 무부하·전기장판(135 W)에서 49.5 °C로 일정. 히터 1.7 kW에서 얼마나 오르는지가 과열 감시 기준이 된다.
- 정전 뒤 동작 `initial_state`: off / on / restore_last / match_input(현재). 켜기 지연 1~600초(`power_restore_delay`) — 돌입 전류 회피용.
- `toggle_after`: 명령과 함께 "N초 뒤 반대로". 투야 카운트다운 데드맨을 그대로 대신한다(5초 시험: 6초째 복귀).

**계측**
- 전력 W·전압·전류·주파수, 누적 Wh, 최근 3분의 분당 mWh(`aenergy.by_minute`).
- 카운터(현재 꺼짐): 켜진 총 시간, 켜진 횟수, 100 W 넘게 쓴 시간. 켜 두면 Pi 없이도 히터 가동 시간을 센다.

**블루투스 게이트웨이**
- BLE 스캔을 스크립트에서 쓸 수 있다(`BLE.Scanner`).
- BTHome 부품: 암호화 BTHome 기기를 MAC+키로 등록(Gen3라 가능). pvvx를 BTHome으로 바꾸면 등록될 가능성이 있으나 미확인.
- Shelly BLU 버튼 학습(`BTHomeControl`).

**자동화**
- 예약(`Schedule`, 일출·일몰 포함 — 플러그가 위치를 자동 감지함).
- 웹훅(`Webhook`): 켜짐·꺼짐, 전력·온도 변화, BTHome 센서 값 변화 때 지정 주소로 HTTP 요청. Pi 없이 텔레그램·시트 경보가 가능하다.
- 스크립트(`Script`, Gen3 펌웨어 1.6.0+): 경량 자바스크립트. `HTTP.GET`, `KVS`, `Timer`, `HTTPServer.registerEndpoint`, **`AES`(ECB·CBC·CFB·CTR·OFB)**.
- 가상 부품(`Number`·`Boolean`·`Text`): 스크립트 설정을 앱에 노출.

**연결**
- Shelly 클라우드가 켜져 있다 → 농막에 인터넷만 있으면 Tailscale 없이 앱 원격 제어·알림.
- Wi-Fi 중계기 기능(`range_extender`). 설정용 자체 AP(`ShellyP-R1`)가 **켜져 있음 → 끌 것**.

## 4. 동파 가드 (`heater/shelly_frost_guard.js`)

Pi와 독립된 마지막 안전망. 사용자 설계 원칙: **"Pi가 카운터(하트비트)를 늘리지 않으면 죽었다고 보고, 플러그가 센서 온도로 동파를 막는다."** 자동 복귀 타이머 없이 하트비트만으로 판단한다.

**입력**
- Pi 하트비트: Pi가 매분 `GET /script/1/hb`. 메모리에만 기록(플래시 마모 없음).
- Qingping CGP22C(평문 0xFDCD): 실내 온도·CO₂.
- pvvx 1층·바닥외부(Mi 암호화 0xFE95): 플러그가 **AES-ECB로 조립한 AES-CCM으로 직접 해독**(태그 검증). 키는 KVS `mbkey_floor1`·`mbkey_out`.
- 기상청 초단기예보: 1시간마다 플러그가 직접 호출. `pageNo=5&numOfRows=6`이면 기온(T1H) 6개만 온다(약 1 KB). 키는 KVS `kma_key`. 기상청 허브가 해외 서버(구글 등)에 잘 응답하지 않아 **국내에 있는 플러그가 부르는** 구조다.

**판단 (30초마다)**
1. 하트비트가 10분 안에 있으면 아무것도 안 한다(Pi가 제어).
2. 실내 = 살아 있는 실내 센서(1층, Qingping) 중 **낮은 값**. 외기 = min(바닥외부 센서, 6시간 예보 최저).
3. 외기가 있으면 1시간 뒤 실내 예측: `T_pred = T_out + (T_in − T_out)·exp(−60/550)` (τ 550분 ≈ 9.2시간, 잠정).
4. `T_in < 3` 또는 `T_pred < 3` → 켬. `T_in > 5` 그리고 `T_pred ≥ 3` → 끔. 그 사이는 유지.
5. 실내 센서 없음·외기만 → 외기 < 5 °C면 켬, 아니면 끔. 아무것도 없음 → 켬(히터 기계식 서모스탯이 과열을 막음).

| 남은 것 | 판단 근거 |
|---|---|
| 센서 + 예보 | 실내 실측 + 외기로 1시간 앞 예측 |
| 센서만(인터넷 없음) | 실내 실측 + 바닥외부 실측 |
| 예보만(센서 고장) | 외기 5 °C 미만이면 켬 → 외기 보상으로 개선 예정(§7) |
| 아무것도 없음 | 켬 |

**보안 성질**: pvvx 위조는 태그 검증으로 막힌다. Qingping은 평문이지만 실내는 낮은 값을 쓰므로 가짜 신호로 "얼게" 만들 수 없고 히터를 더 켜게 할 뿐이다. 전파 방해는 센서 끊김 → 켬. 남은 틈은 녹음한 진짜 pvvx 프레임 재전송(메시지 번호 검사로 막을 수 있음, 미구현).

**상태**: `GET /script/1/status` — 모드, 실내·예측·외기와 출처, 센서별 값·나이·수신 수·RSSI·해독 실패 수, 키 적재 여부(값은 안 실음), 예보 6값·발표 시각, 마지막 판단. `ACT:false`면 판단만 하고 스위치는 안 건드린다("DRY …").

**자원**: 코드 약 9.8 KB, 힙 사용 약 4 KB(최대 9.7 KB, 예보 JSON 파싱 때) / 여유 21 KB.

스크립트 업로드 요령: `Script.PutCode`는 **비ASCII가 섞이면 "bad argument 'code'"로 거절**한다. 주석을 빼고 900바이트씩 `append`로 올린다(설치 도구가 그렇게 함).

기상청 키 넣기(키가 저를 거치지 않도록 사용자가 브라우저에서 직접):
```
http://<플러그IP>/rpc/KVS.Set?key=kma_key&value=<인증키>
```

### 수동 조작의 영향 (11-13 실측·분석)

- 플러그는 바꾼 출처를 남긴다: 버튼 `button`, Pi·앱 RPC `HTTP_in`.
- **손으로 바꾸면 걸려 있던 `toggle_after` 예약이 사라진다**(40초 예약 후 토글 → 45초 뒤에도 반전 없음).
- Pi 제어기는 버튼 조작을 2시간 존중한다(동파 위험·27 °C 상한은 예외) — [HEATER.md](../HEATER.md) "수동 우선 시간".
- 가드는 Pi가 죽었을 때 동파 띠(3~5 °C) 밖에서만 움직이므로, 추울 때 손으로 끄면 30초 안에 다시 켠다.
- ⚠ 집에서 가드를 `ACT:true`로 바꾸지 말 것: 하트비트가 없어 "Pi 죽음"으로 보고 예보만으로 장판을 끈다.

## 6. 교훈

- **운영 중인 스크립트에서 `Script.Eval`로 실험하지 말 것.** AES 인자 형식을 시험하다 잡히지 않은 예외가 나 가드가 멈췄고, **저절로 다시 켜지지 않았다**(시험 모드라 피해 없음). 시험은 임시 스크립트로만 하고 끝나면 지운다(시험 도구들이 그렇게 함).
- 그래서 운영에서는 Pi가 하트비트를 보낼 때 `Script.GetStatus`의 `running`도 확인해, 멈췄으면 `Script.Start`하고 경보를 보내야 한다.
- 문서의 AES 예제는 인자 형식이 틀려 있다. 동작하는 형식은 `AES.encrypt(ArrayBuffer, ArrayBuffer, {mode:"ECB"})`.
- Qingping CGP22C의 BLE 광고는 업로드 주기(최소 10분)에 묶여 있다. 동파 판단엔 충분하지만 1분 제어용은 아니다.

## 7. 남은 일

**농막 설치 때**
1. 플러그를 히터에 연결, 농막 Wi-Fi(핫스팟→Mango)에 재등록, 고정 주소.
2. 설정: 자체 AP 끄기, 기기 비밀번호, `initial_state=on` + 켜기 지연 60초, 전력 한계 약 2,000 W, 카운터 켜기.
3. Pi에서 `shelly_guard_setup.py <IP>` → 상태 확인(센서 3개 수신, 키 적재, 예보 수신) → `--act`.
4. Pi 제어기 전환: `tuya_keys.json`의 히터 항목을 `type: shelly`로(다른 세션의 드라이버), 매분 `/script/1/hb` 호출과 가드 `running` 감시 추가.
5. 현장 시험: Pi 서비스를 일부러 멈추고 10분 뒤 가드가 넘겨받는지, 하트비트가 돌아오면 손을 떼는지.
6. `toggle_after` 데드맨과 하트비트 가드를 함께 둘지 결정(충돌은 없음).

**이후**
- 열모델 학습(11-15 첫 피팅, 11-29 검증)으로 τ·UA 확정 → 가드의 τ 잠정값 교체.
- 실내 센서가 모두 죽었을 때 **외기 보상 제어**: 필요 열량 `UA·(목표−외기)`로 히터 켜짐 비율을 정함(UA 47 W/K, 외기 −10 °C, 목표 5 °C면 약 700 W → 1,763 W 히터 40 %). 목표는 여유를 두어 8 °C.
- 예보 보정: 예보 이력과 바닥외부 실측을 비교해 농막 맑은 밤 편차를 반영.
- pvvx 재전송 방지(메시지 번호 단조 증가 검사).
- 웹훅으로 과열·오류 경보를 Pi 없이 텔레그램에.
- 두 번째 플러그: 선풍기 또는 동파 전용 600 W 히터.
