# 샤오미 센서는 어떻게 동작하고, 왜 게이트웨이를 이렇게 만들었나

학습용 안내서입니다. 저렴한 샤오미 블루투스 온습도계(모델 **LYWSD03MMC**, *Mijia Thermometer 2*)가 어떻게 통신하는지, **GATT**가 무엇인지, 그리고 이 프로젝트가 "센서에 연결해서 읽는" 방식에서 **하이브리드** 설계로 옮겨 온 이유를 설명합니다. 기본적인 프로그래밍을 아는 학생이 따라갈 수 있게 썼고, 조금 더 공부하면 이 저장소의 코드를 이해할 수 있도록 했습니다.

> English version: [SENSOR_GUIDE.md](SENSOR_GUIDE.md)

> **정직하게 말씀드리면.** 샤오미는 이 센서의 블루투스 프로토콜을 공식 문서로 공개하지 않습니다. 여기 나오는 프로토콜 내용은 커뮤니티의 리버스 엔지니어링과 실제 기기 시험에서 얻은 것입니다([README.md](../README.md)의 *개발 메모* 참조). **(코드 근거)** 라고 표시한 부분은 이 저장소의 파일에서 직접 확인할 수 있습니다.

## 1. 배우는 것
- 블루투스 **방송(broadcast)** 과 **연결(connection)** 의 차이
- **GATT 서비스와 특성(characteristic)** 이 무엇인지, 실제 예(이 센서의 이력 버퍼)로 이해하기
- **암호화된 방송**을 해독하는 방법(AES-CCM과 기기별 키)
- 실제 시스템이 왜 두 가지 데이터 경로를 섞어 쓰는지, 각 경로의 비용(배터리, 완전성, 복잡도)
- **무인이고 가끔 오프라인인** 장치를 위한 습관: store-and-forward, 멱등(idempotent) 업로드, 배터리 예산

코드에서 볼 곳:

| 주제 | 파일 |
|---|---|
| passive 해독(연결 없음) | [`passive_current.py`](../passive_current.py) |
| 연결해서 이력 읽기 | [`farmhut_sync.py`](../farmhut_sync.py)(PC), [`passive_gateway.py`](../passive_gateway.py)(라즈베리파이) |
| 둘을 합친 24시간 게이트웨이 | [`passive_gateway.py`](../passive_gateway.py) |
| 운영, 배터리, 사이트 전환 | [OPERATIONS.md](../OPERATIONS.md), [PI_SETUP.md](../PI_SETUP.md) |

## 2. 센서를 1분에 이해하기
- LCD, 저전력 블루투스(BLE) 무선, 코인셀 배터리를 가진 작은 온습도계입니다.
- **계속 측정**하고, 자체 메모리에 **1시간에 레코드 1개**(그 시간의 최고·최저 온도와 습도)를 저장합니다. 이 메모리는 **링버퍼**여서 가득 차면 가장 오래된 것부터 덮어씁니다. 실측으로 **약 5개월**치를 보관합니다 **(README 근거)**.
- 현재 온도·습도·배터리를 BLE로 **방송(broadcast)** 합니다. 순정 펌웨어에서는 방송이 **암호화**되어 있고, 값이 **바뀔 때만**, 온도·습도·배터리를 **따로, 드물게** 보냅니다. 변화가 없으면 온·습도는 대략 10분에 한 번입니다 **(근거: [HEATER.md](../HEATER.md))**.
- 가까운 장치가 **연결**해서 이력을 읽을 수도 있습니다.

즉 같은 센서에 **방송 문**과 **연결 문**, 두 개의 문이 있습니다. 이 프로젝트의 설계는 언제 어느 문을 쓸지에 관한 이야기입니다.

## 3. 5분에 이해하는 저전력 블루투스(BLE)

### 3.1 방송(advertising)과 연결(connection)
```
 방법 A: 방송(ADVERTISING)                 방법 B: 연결(GATT)

   센서 ))))  ))))  ))))                      센서 <───────────> 게이트웨이
        범위 안의 누구나 들을 수 있음                둘만의 양방향 연결
   한 방향, 센서는 누가 듣는지 모름             연결되어 있는 동안 센서의 무선이 바쁨
```
- BLE 장치는 주기적으로 작은 패킷(**광고, advertisement**)을 주변에 외칩니다. 듣는 쪽은 센서에 **아무 비용도 주지 않습니다**. 어차피 외치고 있으니까요. 이를 **passive(수동) 수신**이라고 합니다.
- 질문하고 답을 받으려면 **central**(우리 게이트웨이)이 **peripheral**(센서)에 **연결**합니다. 연결은 센서의 무선을 훨씬 오래 쓰므로 **배터리**가 듭니다. 센서는 보통 **한 번에 한 연결**만 받습니다.

일상 비유: 방송은 **라디오 방송국**(듣는 사람은 신경 쓰지 않음), 연결은 **전화 통화**(양쪽 모두 바쁘고 에너지가 듭니다)입니다.

### 3.2 GATT: 연결된 장치의 데이터 구성
연결하면 장치는 데이터를 작은 파일 시스템처럼 보여 줍니다.

```
서비스(Service)       (관련 데이터의 묶음, UUID로 이름 붙임)
 └─ 특성(Characteristic) (데이터 한 조각, 역시 UUID)
     • 속성: read / write / notify
     • 값: 그냥 바이트
```
- **UUID**: 128비트 식별자입니다. 예: `ebe0ccb0-7a0a-4b0c-8a1a-6ff2997da3a6`.
- **read**: 한 번 물어서 바이트를 받습니다. **write**: 장치에 바이트를 보냅니다. **notify**: *구독*하면 장치가 새 값을 **스스로 밀어 줍니다**(스트림에 적합).
- 바이트의 의미는 제조사가 정합니다. 이 센서는 **공개되어 있지 않아서** 사람들이 리버스 엔지니어링했습니다.

## 4. 방법 A: 방송 엿듣기 (passive)

센서는 측정값을 BLE 광고의 서비스 데이터(16비트 서비스 `0xFE95`)에 **MiBeacon** 패킷으로 담아 보냅니다. 순정 펌웨어에서는 페이로드가 센서마다 다른 비밀 **bindkey**로 **AES-CCM** 암호화되어 있습니다.

### 4.1 패킷의 모양 (리버스 엔지니어링 결과)
```
 [ 헤더 5바이트 ][ MAC? 6 ][ 기능 1~3 ][ 암호문 ... ][ 카운터 3 ][ MIC 4 ]
   frame control (2)                                    카운터의    무결성
   product id    (2)                                    확장        검사값
   frame counter (1)
```
- **Frame control**에는 플래그 비트가 있습니다. `0x08` = 페이로드가 암호화됨, `0x10` = 센서 MAC 주소 포함, `0x20` = 기능(capability) 바이트가 뒤따름.
- AES-CCM의 **nonce**(한 번만 쓰는 값)는 패킷의 일부로 만듭니다. MAC 바이트, product id와 frame counter, 끝쪽의 3바이트 카운터를 이어 붙입니다. 카운터가 패킷마다 달라서 같은 측정값도 같은 암호문이 되지 않습니다.
- **MIC**(메시지 무결성 코드, 4바이트)는 키가 틀렸거나 패킷이 깨졌음을 알려 줍니다. 그러면 해독이 그냥 실패합니다.
- 태그 길이 4바이트와 고정된 추가 데이터 `0x11`도 이 방식의 일부입니다.

**(코드 근거)** [`passive_current.py`](../passive_current.py)가 정확히 이렇게 합니다.
```python
nonce = bytes(sd[5:11]) + bytes(sd[2:5]) + bytes(sd[-7:-4])
mic   = bytes(sd[-4:])
ct    = bytes(sd[i:-7])          # i = 선택 필드 뒤 암호문의 시작
AESCCM(key, tag_length=4).decrypt(nonce, ct + mic, b"\x11")
```

### 4.2 해독 후 안에 있는 것
작은 레코드의 나열이고, 각 레코드는 `종류(2바이트, little endian) | 길이(1바이트) | 값`입니다.

| 종류 | 의미 | 해독 방법 |
|---|---|---|
| `0x1004` | 온도 | 부호 있는 16비트 ÷ 10 → °C |
| `0x1006` | 습도 | 부호 없는 16비트 ÷ 10 → % |
| `0x100D` | 온도 **및** 습도 | 위와 같은 두 값 |
| `0x100A` | 배터리 | 1바이트, % |

### 4.3 bindkey 얻기
키는 센서의 공개 데이터가 아니라 샤오미 계정에 저장되어 있습니다. 커뮤니티 도구 *Xiaomi-cloud-tokens-extractor*로 **본인 계정**에서 읽을 수 있습니다(링크는 맨 끝). **bindkey는 비밀번호처럼 다루세요.** 이 저장소에서는 git에서 제외된 `sensor_keys.json`에 두며, 절대 공개하면 안 됩니다.

### 4.4 passive로 얻는 것과 못 얻는 것
- ✅ **추가 배터리 소모가 없고** 연결 실패도 없습니다.
- ✅ **실시간** 값과 평균 계산에 좋습니다.
- ❌ 게이트웨이가 꺼져 있거나 재부팅 중이거나 범위 밖이면 그 시간의 측정값은 **영영 사라집니다**. 방송은 어디에도 저장되지 않기 때문입니다.
- ❌ 방송은 "지금"만 알려 줍니다. 센서 자체의 시간별 **최소·최대**는 얻을 수 없습니다.

마지막 한계가 방법 B가 필요한 이유입니다.

## 5. 방법 B: 연결해서 이력 읽기 (GATT)

### 5.1 쓰는 특성들
모든 UUID는 `ebe0cc??-7a0a-4b0c-8a1a-6ff2997da3a6` 형태이고, 서비스 자체는 `ebe0ccb0-…`입니다.

| 짧은 이름 | 용도 | 형식 |
|---|---|---|
| `ccb7` | 시간 카운터 | 부호 없는 32비트: **센서가 부팅한 뒤 경과 초** |
| `ccbb` | **최신** 이력 레코드 | 14바이트(아래 참조) |
| `ccba` | **시작 인덱스 포인터** | 32비트 인덱스를 write하면 이력 스트림이 그 레코드부터 시작(비파괴적) |
| `ccbc` | **이력 스트림** | *notify*: 알림 한 번에 14바이트 레코드 하나 |
| `ccc1` | 현재 값 | notify: 부호 있는 16비트 ÷ 100 → °C, 이어서 습도 % 1바이트 |

### 5.2 이력 레코드 하나 (14바이트)
```
 idx (u32) | ts (u32) | maxT (i16) | maxH (u8) | minT (i16) | minH (u8)
 레코드 번호 | 부팅 후 초 | ÷10 → °C | % | ÷10 → °C | %
```
**(코드 근거)** [`farmhut_sync.py`](../farmhut_sync.py):
```python
idx, ts, maxt, maxh, mint, minh = struct.unpack_from("<IIhBhB", b, 0)
```
`<`는 little-endian, `I`는 부호 없는 32비트, `h`는 부호 있는 16비트, `B`는 부호 없는 바이트입니다.

### 5.3 센서에는 진짜 시계가 없다: 시각 환산
센서는 날짜를 모릅니다. 부팅 후 초만 셉니다. 레코드에 실제 시각을 붙이려면:
```
 boot_epoch = now − counter                 # 센서가 부팅한 실제 시각
 wall_time  = now − (counter − record.ts)   # 이 레코드가 끝난 실제 시각
```
연결하는 순간 카운터(`ccb7`)를 읽고, `now`는 게이트웨이의 시계를 씁니다. 그래서 게이트웨이의 **정확한 시계**가 중요합니다. 라즈베리파이는 보통 배터리 시계가 없어서 인터넷 없이 재부팅하면 시간이 틀릴 수 있습니다([TODO.md](../TODO.md)의 H 규칙 참조).

### 5.4 증분 동기화: 없는 것만 달라고 한다
5개월치 이력을 BLE로 통째로 읽으면 센서가 오래 바쁩니다. 대신 이렇게 합니다.
1. **이미 저장한 마지막 시간**의 레코드 인덱스를 구합니다. 코드:
   `idx_of_last = (counter − (now − last_time)) / 3600 − 1`
2. 반올림 오차로 틈이 생기지 않도록 조금 앞에서 시작합니다(**2시간 겹침**). 중복은 받는 쪽에서 걸러 냅니다.
3. 그 인덱스를 `ccba`에 **write**(seek)하고 `ccbc`를 **구독**해서 최신 인덱스에 닿거나 스트림이 멈출 때까지 모읍니다.

```
 게이트웨이                              센서
   │── 연결 ─────────────────────────────▶│
   │── ccb7(카운터) read ────────────────▶│   "켜진 지 얼마나 됐어?"
   │── ccbb(최신 레코드) read ───────────▶│   "가장 최근 레코드 번호는?"
   │── ccba = start_idx write ───────────▶│   "start_idx부터 시작해"
   │── ccbc 구독 ────────────────────────▶│
   │◀──────── 레코드, 레코드, 레코드 … ───│   알림(notify)
   │── 연결 해제 ────────────────────────▶│
```

### 5.5 연결로 얻는 것과 치르는 비용
- ✅ 센서 **자체의 시간별 최소·최대**: *권위 있는(authoritative)* 기록이며, 게이트웨이가 꺼져 있었어도 완전합니다.
- ✅ 공백을 **자동으로 채웁니다**(버퍼가 몇 달치).
- ❌ **배터리**를 씁니다. 연결할 때마다 센서의 무선이 바쁩니다.
- ❌ 불안정합니다. 연결이 실패하고, 스트림이 중간에 멈추고, 한 번에 한 연결만 됩니다(자세한 내용은 6장).

## 6. 구조를 바꾼 이유

첫 버전은 센서에 **연결만** 했습니다(Web Bluetooth를 쓰는 폰 웹페이지와 PC 스크립트). 동작은 했지만 사람이 근처에 있어야 했고, 자주 반복하면 센서 배터리를 소모했으며, 실시간 값은 줄 수 없었습니다. 최종 설계는 라즈베리파이에서 하루 종일 도는 **하이브리드**입니다. 거기까지의 과정을 단계별 커밋과 함께 정리합니다.

| 날짜 | 커밋 | 문제 | 한 일 | 치른 대가 |
|---|---|---|---|---|
| 2026-10-25 | `5b304a8` | Mi Home 그래프를 캡처해 수기로 옮기던 작업. | 폰 웹앱과 PC 스크립트가 **연결(GATT)** 해서 이력을 구글시트에 업로드. | 사람이 근처에 있어야 함. Windows에서 연결이 자주 끊김. 읽을 때마다 배터리 소모. |

## 7. 장단점

### 7.1 센서를 쓰는 세 가지 방식

| | 연결만 | passive만 | **하이브리드 (우리의 선택)** |
|---|---|---|---|
| 센서 배터리 | 자주 하면 큼 | **추가 없음** | 낮음(하루 한 번의 짧은 연결) |
| 실시간 값 | 없음 | **있음** | **있음** |
| 시간별 min/max 정확도 | 정확 | **부정확**(근사) | **정확**(권위 있는 덮어쓰기) |
| 게이트웨이가 꺼졌을 때 공백 | 없음(버퍼) | **유실** | 없음(버퍼로 보충) |
| bindkey 필요 | 아니오 | 예 | 예 |
| 복잡도 | 낮음 | 중간 | **높음** |
| 오프라인 동작 | 일부 | 실시간만 | **가능(store-and-forward)** |

### 7.2 그 밖의 선택들

| 선택 | 장점 | 단점 |
|---|---|---|
| **순정 펌웨어**(플래싱 안 함) | 센서가 벽돌이 될 위험이 없고 출하 상태 그대로 동작 | 암호화된 방송이라 bindkey 필요, 갱신이 느림(안정 시 약 10분), 우리 환경에서 배터리 약 1년(저자 추정) |
| **구글 시트로 직접 업로드** | 서버·브로커·데이터베이스를 운영할 필요 없음. 시트가 저장소, 뷰, 공유, 차트 | Apps Script에 한계가 있음, 실시간 시스템이 아님, 스크립트의 시크릿을 지켜야 함 |
| **로컬 SQLite 큐** | 정전·재부팅·오프라인에도 데이터 손실 없음 | 백업할 파일이 하나 늚, 중복에 안전한 서버 필요 |
| **하루 1회 이력 동기화** | 센서 배터리 절약 | 시트의 이력이 최대 하루 늦음 |
| **라즈베리파이 게이트웨이** | 항상 켜져 있고 저렴하며, BLE에서 Linux/BlueZ가 Windows보다 안정적 | 작은 컴퓨터를 관리해야 함(업데이트, 시계, 전원) |

### 7.3 공부해 볼 만한 대안
**pvvx/ATC** 같은 커스텀 펌웨어는 센서가 **평문의 개방형 형식**(예: **BTHome** 표준)으로 방송하게 해서 해독이 필요 없고 갱신도 더 자주 할 수 있습니다. 대신 플래싱 위험이 있고 장치의 동작이 달라집니다. 이 프로젝트는 일부러 순정 펌웨어를 유지했습니다. 둘 다 타당한 공학적 선택입니다.

## 8. 히터 제어와의 관계
히터 제어기는 게이트웨이가 쓰는 작은 파일에서 최신 온도를 읽습니다. 이 안내서의 세 가지 사실이 제어기의 동작을 정합니다.
1. **데이터는 낡을 수 있습니다.** 안정된 센서는 약 10분에 한 번만 방송할 수 있고, 게이트웨이 파일이 조금 더 늦을 수 있습니다. 그래서 제어기는 **45분**보다 오래된 데이터를 "알 수 없음"으로 봅니다([`heater_config.json`](../heater_config.json)의 `stale_temp_min`, 근거는 [HEATER.md](../HEATER.md)). 동파 방지 모드에서 온도를 알 수 없으면 "히터를 **켠다**"입니다.
2. **방송은 한 순간의 스냅샷입니다.** 제어 루프는 초 단위 정확도가 아니라 히스테리시스와 안전한 기본값을 중심으로 만들었습니다.
3. **이력 경로는 기록용이지 제어용이 아닙니다.** 제어는 실시간(passive) 경로를 쓰고, 연결 경로는 장기 기록을 완성하는 데만 씁니다.

## 9. 재사용할 수 있는 설계 교훈
1. **"실시간"과 "권위 있는 기록"을 분리하세요.** 싼 경로로 지금 값을 보고, 정확한 경로로 나중에 기록을 바로잡습니다.
2. **배터리를 예산으로 다루세요.** 연결마다 비용이 있습니다. 일정을 정하고, 증분으로 읽고, 쓸모없을 때(오프라인)는 건너뜁니다.
3. **네트워크는 불안정하다고 가정하세요.** 먼저 로컬에 저장하고 가능할 때 올립니다(**store-and-forward**).
4. **업로드를 멱등하게 만드세요.** 같은 레코드가 두 번 올 수 있으므로 받는 쪽은 `(센서, 시각)`을 키로 삼아 중복을 무시합니다.
5. **조용히 실패하지 마세요.** 잘림 버그(`409c729`)가 위험했던 이유는 성공처럼 *보였기* 때문입니다. 기대한 것과 받은 것을 로그로 남깁니다.
6. **하드웨어 한계를 존중하세요.** 한 번에 한 연결, BlueZ에서는 스캔과 연결이 겹칠 수 없습니다. 공유 자원에는 락을 겁니다.
7. **실제 장치에서 시험하세요.** 이력 이어받기 수정은 스트림을 일부러 멈춰서 검증했습니다.
8. **인터페이스는 작게 유지하세요.** 게이트웨이와 히터 제어기는 파일 하나만 공유합니다. 한쪽이 죽어도 다른 쪽은 계속 돕니다.
9. **비밀은 저장소 밖에 두세요.** 키와 비밀번호는 제외된 파일이나 환경 변수에 둡니다.

## 10. 연습문제
수준에 맞는 것을 고르세요.

**초급**
1. 센서 하나에 대해 두 데이터 경로(방송과 연결)를 그리고, 각각의 배터리 비용을 한 문장으로 쓰세요.
2. 이력 레코드가 16진수로 `34 12 00 00 | 10 0E 00 00 | E6 00 | 3C | D2 00 | 38`입니다. `idx`, `ts`(초), 최고·최저 온도와 습도를 해독하세요. (힌트: little-endian, 온도는 ÷ 10)
3. 센서 카운터가 3,600,000초이고 레코드의 `ts = 3,595,000`입니다. 게이트웨이 시계는 12:00:00입니다. 이 레코드는 언제 끝났나요?

**중급**
4. [`passive_current.py`](../passive_current.py)를 읽고 광고 바이트에서 최종 온도까지 단계 순서를 쓰세요. 키가 틀리면 어떻게 되나요?
5. 객체 목록(`종류 | 길이 | 값`)을 해독하는 짧은 함수를 쓰고, 직접 만든 패킷으로 시험하세요.
6. 증분 동기화에서 2시간 겹침이 왜 유용한지, 서버가 겹친 시간을 어떻게 처리하는지 설명하세요.

**고급**
7. SQLite로 **store-and-forward**를 모의하세요. 시간별 값을 만들고, 하루 동안 "오프라인"이 되었다가 묶음으로 업로드하세요. 업로드를 멱등하게 만들고, 행이 사라지거나 중복되지 않음을 증명하세요.
8. **구멍을 인식하는 이어받기**를 구현하세요. 무작위로 멈추는 가짜 스트림을 만들고, 빠진 레코드 번호를 찾아 구멍만 다시 요청하는 루프를 쓰세요.
9. 순정 펌웨어와 개방형 방송 형식(BTHome 등)을 비교해 얻는 것과 잃는 것을 쓰고, 인터넷이 없는 마을 센서망이라면 무엇을 고를지 정하세요.
10. **여러분 자신의 문제**(예: 온실, 쌀 창고)에 같은 시스템을 설계하세요. 무엇이 "실시간"이고 무엇이 "권위 있는 기록"인지, 네트워크가 끊기면 어떻게 되는지, 뭔가 고장 났을 때 안전한 상태는 무엇인지 쓰세요.

<details>
<summary>초급 연습문제 정답</summary>

- **2번:** `idx` = 0x1234 = 4660, `ts` = 0x0E10 = 3600초(부팅 1시간 뒤), `maxT` = 0xE6 = 230 → **23.0 °C**, `maxH` = **60 %**, `minT` = 0xD2 = 210 → **21.0 °C**, `minH` = 0x38 = **56 %**.
- **3번:** `counter − ts` = 3,600,000 − 3,595,000 = 5,000초 = 1시간 23분 20초. 레코드는 12:00:00 − 1:23:20 = **10:36:40**에 끝났습니다.
</details>

*안전:* 센서의 bindkey나 비밀번호를 공개된 곳에 공유하지 마세요. 본인의 센서와 본인의 계정만 사용하세요.

## 11. 용어집
- **BLE(Bluetooth Low Energy)**: 작은 센서가 쓰는 저전력 블루투스.
- **광고(Advertising)**: BLE 장치가 범위 안의 누구나 들을 수 있게 주기적으로 방송하는 작은 패킷.
- **Passive 스캔**: 묻거나 연결하지 않고 광고만 듣는 것.
- **Central / peripheral**: 연결하는 쪽(게이트웨이)과 연결받는 쪽(센서).
- **GATT**: 연결된 BLE 장치가 데이터를 서비스와 특성으로 정리하는 방식.
- **서비스 / 특성(characteristic)**: 데이터 묶음 / 서비스 안의 데이터 한 조각. 둘 다 **UUID**로 이름 붙음.
- **Read / write / notify**: 한 번 묻기 / 데이터 보내기 / 구독한 뒤 장치가 업데이트를 밀어 주기.
- **MiBeacon**: 샤오미의 광고 형식(서비스 `0xFE95`).
- **Bindkey**: MiBeacon 페이로드를 해독하는, 기기마다 다른 비밀 키.
- **AES-CCM**: 무결성도 검사하는 암호화 방식. **nonce**를 쓰고 **MIC**(메시지 무결성 코드)를 만듦.
- **Nonce**: 메시지마다 한 번만 쓰는 수. 같은 데이터가 같게 암호화되지 않게 함.
- **링버퍼**: 가득 차면 새 데이터가 가장 오래된 것을 덮어쓰는 고정 크기 메모리.
- **히스테리시스**: 스위치가 오락가락하지 않도록 두 개의 임계값(켜짐, 꺼짐)을 쓰는 것.
- **데드밴드**: 일부러 무시하는 작은 변화.
- **Store-and-forward**: 먼저 로컬에 저장하고 연결이 될 때 보내는 방식.
- **멱등(Idempotent)**: 같은 연산을 두 번 해도 한 번 한 것과 결과가 같음.
- **BlueZ**: 리눅스의 블루투스 소프트웨어 스택(라즈베리파이에서 사용).
- **Little-endian**: 여러 바이트 숫자를 가장 낮은 자리 바이트부터 저장하는 방식.
